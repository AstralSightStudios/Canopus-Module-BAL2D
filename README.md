# BAL2D：手表上的蔚蓝档案记忆大厅

BAL2D 是一个 Canopus 模块（`ba_l2d`）。它让小米手环 10 Pro（固件 3.101.043）把蔚蓝档案的记忆大厅（Spine 4.2 动画）作为表盘的一个图层播放：角色静置时循环待机动画，点一下说话（游戏原版台词显示在对话气泡里），拖动头部摸头，触摸有原版风格的点击特效，用 VGLite GC355 GPU 绘制。

**本项目不包含、也不分发任何游戏素材。** 角色素材由用户自己从游戏中提取，或由插件从第三方社区仓库直接下载到手机（见“在线角色库”），在手机上的 AstroBox 插件里编译成手表角色包；素材仅限个人使用，请勿分享。

## 组成

| 目录 | 作用 |
|---|---|
| `crates/bal2d-spine` | Spine 4.2 运行时（`no_std`）：二进制骨骼读取与写出、动画状态、约束、物理。与官方 spine-core 4.2 逐帧对比（`examples/golden.rs`）。 |
| `crates/bal2d-render` | 绘制列表（含裁剪附件）、把三角形按仿射聚类成 GPU 路径（`Paths`）。 |
| `crates/bal2d-pack` | `.bal2d` 角色包格式：骨骼、图集、GPU 贴图页、烘焙背景、预烘焙待机、互动参数。 |
| `crates/bal2d-core` | 大厅逻辑：开场 → 待机、点击说话、拖动摸头/视线跟随；预烘焙待机的播放。 |
| `crates/bal2d-compiler` | 手机端编译器：模拟所有会播放的动画，剔除看不见的部分（含始终被别的骨骼完全挡住的整个骨骼），简化网格，按屏幕密度裁切重采样贴图，烘焙静态背景，把待机循环预烘焙成 GPU 调用，删除不会播放的动画与无用时间轴。 |
| `crates/bal2d-preview` | 软件渲染预览（插件预览图、主机工具）。 |
| `crates/bal2d-face` | 给成品表盘（BIN/MWZ）加入角色图层。 |
| `crates/bal2d-proto` | 插件与模块之间的 CanopusConnect 协议：编解码、手表端接收、手机端发送。 |

| `tools/bal2d-tool` | 开发工具：渲染、编译、对比、基准、表盘信息与 patch。 |
| `tools/bal2d-link-cli` | 通过 Mirage 的 AstroBox 桥运行插件同款发送器（安装、列表、统计、批量基准）。 |

| `examples/lua-face` | 带角色图层的 Lua 表盘示例。 |

## 使用方式

1. 在手表上安装并启用 `ba_l2d` 模块（Canopus）。
2. 在 AstroBox 安装插件 `BA 记忆大厅导入器`，连接手表。
3. **导入角色**：添加某个大厅的 `.skel`、`.atlas` 和全部 `.png`（或一个包含它们的 zip；有背景骨骼的大厅一并加入；可选加入社区整理的 `interactions.json` 获得原版摸头参数）。文件按内容识别，安卓上没有扩展名的文件名也能配对。默认按头部居中取景；“打开取景器”会先生成整个场景的小预览，上面的方框就是手环屏幕显示的范围：拖动方框移动、拖动右下角缩放，也可以用滑块（触屏上拖动不灵时用滑块）。待机之外，开场、对话、摸头可以各用一个取景（“单独取景”），手环上会在这些阶段之间用 0.6 秒平滑切换；编译时会照顾到每个取景里能看到的内容和清晰度。选好画质后“编译并预览”（显示进度），确认后“安装到手表”。插件总共只有 128 MiB 内存，编译时贴图按行流式解码，不会整页解码大图集。
4. **表盘图层**：在“表盘图层”页选择一个成品表盘（`.bin` / `.mwz`），指定角色插在第几层（一般是背景之上），生成后加入安装队列或保存。生成的表盘使用新的表盘 ID（`B2D` 开头）并在名称后加 “ BA”，与原表盘并存，不会因为同 ID 而安装失败。安装并切换到这个表盘，角色就出现在该层：时间等组件叠在角色上方，头部区域仍可摸头，其他区域的滑动照常交给系统。屏幕最上方 40 像素始终归系统：从这里开始的下拉（消息中心）不会被当作摸头，即使角色的头在那里；摸头请从头部稍下方开始。
5. **Lua 表盘 / 其他应用**：任何显示 `/data/canopus/m.ba_l2d/layer.bin` 的 LVGL 图片对象都会被模块接管为角色图层，它在对象树中的位置就是层级（不设置尺寸时占满全屏）。模块启动时会写入这个文件（16×16 透明图），所以模块没运行时表盘照常显示。示例见 `examples/lua-face/main.lua`：

   ```lua
   lvgl.Image(root, { src = "/data/canopus/m.ba_l2d/layer.bin", x = 0, y = 0 })
   ```
6. 没有角色图层的表盘：可在插件“手表上的角色”页或手表上的“BA 大厅”应用里打开“全屏显示”，角色会全屏显示在表盘最上层。它是表盘的一部分：滑到启动器或打开应用时不会盖住它们，滑动照常翻页，被它盖住的表盘内容也不再重绘。Lua 表盘不支持全屏显示，请在 Lua 里放 `layer.bin` 图片。

手表上的“BA 大厅”应用显示当前角色、显示方式与性能，可直接切换到下一个角色、开关全屏显示和流畅优先。

### 在线角色库与对话气泡

- **在线角色库**（“导入角色”页最上方）：点“载入角色列表”，插件下载第三方社区整理的大厅清单（约 280 个记忆大厅，按中文名、韩文名或 ID 搜索），点某一行的“下载并导入”即可：插件在手机上下载这个大厅的 `.skel`、`.atlas` 和图集用到的全部 `.png`（有背景骨骼的大厅，如星野、明里、柚子，一并下载），按当前的编译设置编译并预览；连着手表且“下载后直接安装到手表”开着（默认）时直接安装。想先调整画面范围就点旁边的“下载并取景”：只下载素材并打开取景器，不编译也不安装，调整好后点“编译并预览”“安装到手表”。手动添加文件的方式保持不变。
- **素材来源**：大厅素材来自社区仓库 [asdfdsa12/BA-Spine-Viewer-Asset](https://github.com/asdfdsa12/BA-Spine-Viewer-Asset)（清单为 [asdfdsa12/BA-Spine-Viewer](https://github.com/asdfdsa12/BA-Spine-Viewer) 的 `memorial/Characters.json`），中文名来自 [SchaleDB](https://schaledb.com)，大厅与学生的对应关系及对话台词来自 [electricgoat/ba-data](https://github.com/electricgoat/ba-data) 的游戏数据表（`MemoryLobbyExcelTable`、`CharacterDialogExcelTable`）。这些都是第三方仓库，由手机直接从它们（或下面的 CDN 线路）下载；本项目不托管、不转存、也不分发其中任何文件，素材仅限个人使用。
- **下载线路**：“自动”依次尝试 jsDelivr（cdn）、jsDelivr（fastly）、GitHub 直连，记住本次会话里成功的那一条；也可以固定为 jsDelivr 或 GitHub 直连，或选“自定义”填一个加在 GitHub 原始链接前的代理前缀（如 `https://ghfast.top/`，失败时再走自动线路）。中国大陆访问 `raw.githubusercontent.com` 常常不通，一般用 jsDelivr 或自定义前缀。JSON 表格按 gzip 下载（对话表约 2.3 MB，解压后约 15 MB，边解压边解析，只保留记忆大厅台词）。
- **对话气泡**：编译设置里的“气泡文字”可选简体中文（默认）、繁體中文、日本語、English 或关闭。角色包里写入大厅会播放的每段对话的台词（每句的显示时长、是否是内心独白），手表在对话时显示气泡。简体中文由游戏繁体中文（台服）台词逐字转换，字表取自 [OpenCC](https://github.com/BYVoid/OpenCC) 的 `TSCharacters.txt`（Apache-2.0，见 `plugins/astrobox-bal2d-import/src/ts_chars.txt` 与 `scripts/gen_ts_table.py`）；国际服数据表里还没有的新角色用日服台词。手动导入的大厅按骨骼、图集文件名或图集里的贴图页名找到对应学生，同样带台词；离线时照常编译，只是没有气泡。对话表每次打开插件只下载一次。
- **手表上的气泡**：对话开始时在屏幕下方弹出白色圆角气泡（浅蓝描边、藏青文字、尾巴指向角色头部，略微上浮出现），一句接一句按游戏里的时长显示，最后一句结束后消失；内心独白用浅灰蓝的气泡和圆点尾巴。文字用手表自带的 MiSans 24 px（简繁中文与日文假名都有字形），手表按约 11 个汉字一行重新均匀断行（游戏的断行是给更宽的气泡写的），不让标点落到行首；气泡宽度随文字。气泡是表盘容器里最上层的 LVGL 对象，压在表盘控件之上，不接收触摸；每段对话新建、结束即删（在 LVGL 里事后改样式或调层级的标签在手表上画不出背景）。没有台词的旧角色包照常播放，只是没有气泡。
- **点击特效**：按下时一圈浅蓝光环向外扩散，中心一团柔光，几个小三角向四周飞散；拖动（含摸头）时手指经过的地方留下渐隐的光点。特效是三张开机时生成的小贴图（共约 24 KB），每个粒子一次 GPU 绘制，和角色画在同一帧里（同时最多 32 个粒子）。
- **点击判定**：很多大厅有全屏的视线跟随拖动，按下 0.1 秒后就开始；手指点一下往往超过这个时间，过去会被当成拖动而不说话。现在 0.35 秒内松开、移动不超过 14 像素都算点击（对话中除外）。`bal2d-core` 的 `tapsim` 例子按手表的方式模拟点击并打印哪些点击开始了对话。

## 渲染与性能

- **待机预烘焙**：手表大部分时间都在播待机动画，而真机上逐帧动画、蒙皮、聚类的 CPU 开销是瓶颈（实测重度大厅绘制 111 ms，约为计时模型的 3 倍）。编译器把成品角色包装进与手表相同的大厅逻辑里播放到待机，按每秒 30 帧（循环很长时更少；角色包超过 2 MB 时减半）记录每一层待机循环的 GPU 调用：每帧每个附件分成哪几组三角形、每组用哪个仿射（按组内全部顶点最小二乘拟合，误差 ≤ 1 像素，GPU 调用比逐帧聚类少约三成），仿射存成该组三个参考点的屏幕坐标（1/16 像素定点，帧间差分）。只播放待机循环时（没有对话、拖动、镜头过渡），手表直接按帧取调用，相邻两帧之间对矩阵线性插值，不跑 Spine 动画、不蒙皮、不聚类；手指一按下就把骨骼补到当前时刻，回到逐帧计算。相邻组共用的顶点取各组位置的平均，路径严丝合缝（否则会出现一像素宽的发丝缝）。待机循环里被裁剪附件裁切的槽位（如 CH0348 的两处饮料阴影）几何每帧都变，不能预烘焙：它们在调用流里留一个标记，手表照常给这一层摆姿势，只对这几个槽位做蒙皮与聚类，其余照样按预烘焙数据绘制。`bal2d-preview` 的 `idlecheck` 例子逐帧对比预烘焙与逐帧计算的画面（参考大厅 PSNR 31–36 dB，肉眼无差别）。
- **网格简化**：编译时记录每个网格顶点在所有模拟帧里的世界坐标，把内部顶点合并到相邻顶点（半边折叠），条件是原网格上任意一点（顶点、边中点、三角形重心）在所有帧里都不偏离超过 0.5 像素、纹理空间里不翻折；轮廓顶点不动。参考大厅的三角形减少约四分之一到三分之一，画面 PSNR 50 dB。
- **GPU 路径**：每个附件的可见三角形按“同一张纹理、同一个仿射”（误差 ≤ 0.75 像素）聚成一条 VGLite 路径，用 `vg_lite_draw_pattern` 一次画完。聚类一遍完成：每个三角形只读一次，先试它上一个加入的组，再试其余的组，结果与“每组扫描一遍剩余三角形”完全相同，测试次数减半。路径用 16 位定点坐标（1/8 像素精度），数据量是浮点路径的一半；共享顶点取整一致，不会出现裂缝。插件预览图按同样的聚类方式软件渲染，所见即手表所得。
- **静态背景烘焙**：编译时找出绘制顺序最底部、在待机/对话/摸头/拖动/物理下都不变的槽位，全精度合成为一张 RGB565 图；手表上每帧先贴这张图再画其余部分。只在开场动画里移动的背景，开场结束后才切换到烘焙图。
- **贴图**：ARGB8565（565 颜色 + 8 位透明度，与 16 位屏幕精度一致，无抖动颗粒），只保留实际可见的部分，并按屏幕上的最大缩放密度重采样。图集中 90/180/270 度旋转的区域都会还原。
- **网格裁剪**：编译时记录每个三角形是否出现在屏幕（含 24 像素余量）内，从未出现的三角形及只被它们使用的顶点（连同变形时间轴的对应数据）被删除，手表每帧少做大量蒙皮与剔除（参考大厅的绘制列表三角形减少 5–43%）。
- **内存**：动画曲线只存 Bezier 控制点（与官方运行时数值一致，内存约为 1/4.5）；不会播放的动画、没有可见内容的槽位/骨骼的时间轴在编译时删除。同一关键帧的多个通道（位移的 X/Y、颜色的 RGBA）在 Spine 里通常是联动的同一条缓动：把每个通道的关键帧映射到 0–1 后控制点相同。读取骨骼时（手表上和插件里都一样，角色包格式不变，旧包也受益）这样的关键帧只存一份归一化的缓动，求值时按各通道的起止值还原（与原控制点相差不超过浮点舍入，不动的通道配任何缓动都一样）。CH0334（武装爱丽丝，开场动画 28.8 秒、2.8 万个关键帧）加载后的骨骼内存从 4.7 MB 降到 3.9 MB，Neru 少 0.35 MB，星野少 0.14 MB；画面与改动前 PSNR 94 dB（只有个别边缘像素差一级）。
- **贴图分页**：手表上每张贴图页是堆里的一整块。标准画质的单层大厅原先是一张约 2.7 MB 的页，而真机日志显示切换几次角色后最大的空闲块会降到 2.6 MB 左右，于是第二、第三次加载就因为找不到这么大的一块而失败（插件显示“手表内存不足”），即使总空闲还有 8 MB。现在每页最多 50 万个纹素（约 1.4 MB）：超出时按绘制顺序把区域切成面积相当的几段、各自打包，所以一帧里大约只在分界处换一次页（每换一次页结束一批绘制；CH0334 每帧的批次 24.8 → 25.8）。
- **换角色时不切碎内存**：模块自己的渲染目标（RGB565，约 315 KB）原先在第一个角色加载完、图层挂上之后才分配，顶点与路径缓冲、批量命令流也是加载完才按角色的大小分配，而它们在卸载角色时都不释放，于是每次换角色它们都留在上一个角色的内存中间，把空闲内存切成两段（真机日志：启动时最大空闲块 8049 KB，换一次角色后 5384 KB，再换后 2689 KB）。现在渲染目标在模块启动、加载任何角色之前按全屏分配，图层尺寸变化（先报 16×16 再报全屏）只是改用其中一部分；工作缓冲在卸载时一起释放，由下一个角色在贴图之后重新分配。Mirage 上在 CH0334、星野、Neru 之间来回切换，卸载后的空闲稳定在 9.8 MB，最大空闲块第二次切换后就不再变小（剩下的分割来自加载后才创建、一直存在的 LVGL 对象）。
- **加载顺序与重试**：预烘焙最后补装时，原先要求一整块“预烘焙展开 + 压缩段 + 派生数据 + 768 KB 余量”的连续内存（CH0334 的 950 KB 预烘焙要 2.3 MB 的一整块），其实这几部分各自分配、余量只要求总量：现在与提前加载一样，只要求最大的一块放得下、总量留足余量，CH0334 和 Neru 的预烘焙因此能在贴图之后装上。提前装的预烘焙可能把空闲内存切开，丢掉后留下的洞和别的空闲块不相邻，下一页贴图仍放不下（Mirage 上 CH0334 第一次加载就这样失败）：这时整个角色包从头再加载一次，贴图先进、预烘焙最后。注意贴图在 GPU 还没确认原格式贴图不超时（或自检判它不可用）时按 32 位上传，比编译时估的多三分之一（CH0334 两页共 3.6 MB）。
- **帧调度**：最高 30 fps。熄屏、息屏显示、打开应用、滑到启动器 / 控制中心等页面盖住表盘时都不画（这个固件打开应用并不切换 LVGL 的当前屏幕，而是隐藏表盘所在的窗口；启动器与控制中心是从旁边滑入、盖在表盘上的页面，LVGL 仍会画被盖住的表盘，模块按“先前见过它在屏幕外或隐藏、现在盖满屏幕的屏幕大小的后续兄弟对象”识别它们；一出现就盖满屏幕的对象算表盘自己的，Lua 表盘在图层之后才建的全屏部件因此不会被误认成页面）。每帧之后测量 LVGL 因这一帧重绘屏幕的耗时（主要是等屏幕的 TE 信号与整屏传输；插件里显示为“屏幕刷新”）。重绘期间界面任务同样被占用，所以之后再让它空闲“本帧 + 重绘”的 1/6（至少 4 ms；最初是 1/3、重帧 1/2，真机上白白损失了帧率），手表自身的界面、蓝牙与传感器始终有机会运行。模块启动或手机连接状态变化后的 30 秒内，如果手机还没连稳且帧较重（帧加重绘 ≥ 45 ms），每 2 秒再停画 250 ms，给连接与认证留出完整的时间窗（以前只要没连着就一直停，没带手机时每 2 秒卡一下）；轻的帧（如预烘焙待机）之间本来就有足够空闲，不再停画（否则每 2 秒卡一下）。帧定时器在这个固件上平均晚触发几毫秒，所以提前 3 ms 请求，30 fps 上限也扣除测得的迟到量。这些比例是在 Mirage 上按蓝牙稳定性定的；**流畅优先**（插件“手表上的性能”或手表应用里的开关）只留本帧加重绘的十二分之一（至少 2 ms），连接中的停画照旧，用来在真机上确认手表的蓝牙和界面是否需要那么多空闲。它默认关闭：在 Mirage 上，开启后重度角色全屏叠在动态表盘上时手机的请求会超时（`scripts/btstress.py --fluent`），默认节奏下同一测试全部成功；真机是否同样如此要实测。（Mirage 上曾出现重度角色全屏叠在动态表盘上时手机连不上：原因是模拟器自身的全局锁在 macOS 上不公平，已在模拟器里修复。）
- **图集矩形直接贴图**：一组三角形如果正好是图集里的一个轴对齐矩形、且整组刚性移动（区域附件、单格网格，角点误差 ≤ 0.25 像素），就不生成路径，改用 `vg_lite_blit_rect` 贴这块矩形（没有三角形要组装、聚类，也没有路径数据）；四顶点两三角形的附件直接按共享对角线识别，不进入聚类。驱动把矩形本身当作贴图（原点写进 0x0A2D，矩阵作用于矩形内坐标）。大量小部件的大厅（如 Neru，约一半调用）受益。是否启用由 GPU 自检里旋转、缩放、调色后的图集矩形贴图结果决定，不对就照旧画路径。
- **GPU 与 CPU 并行**：背景图贴完、以及每 48 次绘制，就把已有的命令交给 GPU（`vg_lite_flush`），GPU 光栅化的同时 CPU 继续生成后面的路径，帧末等待 GPU 的时间明显缩短。
- **直接绘制（默认）**：画面不再先画进模块自己在 PSRAM 里的 RGB565 缓冲区、再由 LVGL 整屏拷到屏幕，而是在图层对象的 DRAW_MAIN 事件里直接画进 LVGL 的屏幕图层（片上 SRAM 里的 RGB888 帧缓冲，0x20000000），时机正好在它下面的表盘内容之后、上面的时间等组件之前。图片本身设为全透明（LVGL 不画它），COVER_CHECK 仍回答“完全覆盖”，所以它下面的内容照旧跳过。GPU 每个混合像素的目标读写从 PSRAM 挪到了 SRAM，每帧还省掉一次整屏拷贝和模块的 322 KB 缓冲区读写。LVGL 把屏幕分上下两半刷新：第一半就把整个图层画完，第二半如果 LVGL 也是从这个图层画起就直接跳过；同一帧里同一块区域再刷新一次（上面的组件变了）就照常重画。图层被滑动（翻页、上划）时、或被别的页面盖住时，改回模块自己的缓冲区，让 LVGL 按自己的帧率拷贝，系统动画不受拖累。手表应用与插件里可以关掉直接绘制做对比。每次开机的前 8 帧直接绘制会做读回校验：画之前 CPU 在要画的区域里写 4 个标记像素，画完（等 GPU 完成）再读回；这一帧会清屏或盖满整个区域，标记若全部还在，说明 GPU 的输出没有进 LVGL 的缓冲区（GPU 看到的地址不同或有缓存挡着），本次开机之后一律改用缓冲绘制。结果显示在手表状态页和插件里。（系统自己在缓冲方式下就是用 GPU 往同一块 0x20000000 写的，Mirage 的 GPU 命令抓取可以看到，所以这个地址在真机上 GPU 可达。）
- **批量绘制**：厂商驱动每次 `vg_lite_draw_pattern` 都把约 34 个状态寄存器连同路径拷进位于非缓存内存的命令缓冲区，还要进出临界区、上报电源管理活动；真机上每次约 150 µs，重度帧的三分之一耗在这里。现在同一张贴图、同一种混合方式的一串绘制只调用一次驱动：这次调用的路径是“已上传路径”，驱动照常设好贴图、混合与路径矩阵，然后 CALL 到模块自己写的命令流，命令流里每次绘制只重设真正不同的寄存器（图像坐标生成器、颜色、细分窗口）并附上路径。生成器的数值按驱动自己的算法计算（逆矩阵、像素中心采样、双线性半个纹素偏移、按贴图尺寸归一化），与 Mirage 捕获的驱动结果逐位相同或只差浮点最后一位。GPU 自检用两次批量绘制核对每次绘制各自的贴图位置与着色，不对就退回逐次调用驱动。
- **轮廓路径**：预烘焙的每一组三角形在加载时求出外轮廓（只出现一次的边按原三角形方向连成闭环，非零填充正好覆盖三角形的并集，孔洞与镜像都正确；边被同向共用、三条以上共用或无法闭合时照旧画三角形）。一组只画一个多边形，不再逐个三角形：参考大厅每帧的路径数据少 3.5–4.3 倍（Hoshino 66.6 → 19.2 KB），内部顶点也不用再变换，画面与原来逐像素一致（PSNR 不变）。
- **画质自适应**：实时绘制的仿射聚类误差从 1.0 像素起（与预烘焙相同；原先从 0.75 像素起，对话时 GPU 调用多约四分之一）；如果一帧连同重绘超过约 31 ms（保持不了 24 fps），每 3 秒放宽一级到 1.25 像素（GPU 调用再少 10–15%），有余量时收回，轻的大厅可以回到 0.75 像素（“精细”）。只按有实时图层的帧调整：聚类只用于实时图层，预烘焙的帧很轻，过去会在待机时把档位收回，每次对话都从最费的分组开始，要过 3–6 秒才放宽，差不多一段对话就过去了。手表应用里显示当前档位。
- **为 Cortex-M33 写的数学**：M33 的 FPU 只有单精度，libm 的 `sinf`/`cosf` 内部用双精度，在手表上会变成软件浮点调用（按指令计时的模型里，它们曾占重度大厅全部 CPU 时间的五分之一）。骨骼变换改用单精度实现（误差 < 2e-7，按 90° 精确归约角度）；每帧执行的 crate 按速度编译（Canopus 默认按体积），蒙皮与路径循环去掉了逐元素边界检查。改动前后，8 个参考大厅 150 帧的全部 GPU 调用逐位相同（`examples/calldump.rs`）。
- **不重复计算不变的动画数据**：所有关键帧都相同的网格变形时间轴（例如 Hoshino 的待机动画里 40 条、每帧 2.5 万个浮点数），在槽位已经是这组值时不再逐顶点重算；数值与贝塞尔控制点都不变的曲线跳过查找与插值；同一关键帧的多个通道（RGBA、XY）共用一条贝塞尔时间曲线时只求一次采样位置。结果逐位不变（8 个大厅 600 帧的 GPU 调用摘要一致），Hoshino 的动画更新在模型里从约 8 ms 降到约 3 ms。
- **分步加载**：切换角色时，骨骼、每张贴图页、烘焙背景分在不同帧加载，加载期间手表界面不卡死。

## 真机与模拟器

模拟器能跑不等于真机能跑。下面这些差别已经专门处理过：

- **缓存一致性**：真机的 PSRAM 有缓存，Mirage 没有。CPU 写好的贴图、烘焙背景在交给 GPU 前都做缓存回写；GPU 画出的帧只由 GPU 读取（在 Mirage 上对渲染目标加读写观察点运行 20 秒：除 PNG 解码器检查前 8 字节文件头外，没有任何 CPU 访问）；路径数据由驱动复制进命令缓冲，复用安全。
- **GPU 自检**：模块启动后第一帧，用渲染时依赖的每种功能各画一个 4×4 小方块（S16/FP32 路径、四种贴图格式、PAD 边缘、调色、四种混合、背景贴图、小块与大块贴图的缓存回写、旋转缩放调色的图集矩形贴图、一次驱动调用里的两次批量绘制），经非缓存地址读回逐一比对。有问题就自动换用备选方案：FP32 路径、绕过缓存写贴图、把该格式的贴图展开为 32 位（内存不够时保持原格式）、透明边缘、逐次调用驱动；未通过的探针名直接显示在手表应用里；结果在插件“手表上的性能”和手表应用里显示。所有备选方案都在 Mirage 上强制启用过（开发文件 `selftest-force`），画面与正常时一致。每个探针单独提交、单独等 GPU、立即读回，并记下驱动调用与等待的返回码：一个探针让驱动或 GPU 出错，不会连带后面的探针（第三次真机测试里，第 5 个探针之后全部失败，连和通过项完全相同的绘制也失败，像是一次出错丢掉了整批命令）。全部画完后再隔 30 ms 读一次，并在作废缓存行后经缓存地址读一次；任何一次读到正确颜色都算通过，三种读法各自的结果写进日志和手表状态页，用来区分"GPU 写得晚""写进了别处"和"功能本身不对"。另加一个探针，在目标最右端重复 S16 绘制，检查结果是否和位置有关。
- **GPU 超时与分批提交**：固件的 VGLite 驱动等一次提交最多 100 ms，超时后复位 GPU 并向调用方报告成功，这一批里还没画的绘制全部丢失，正在画的图形只剩一部分扫描行（真机录像里角色大块消失一帧、边缘呈台阶状，后提交的工牌仍在）。现在每次提交的绘制量按屏幕矩形面积累计，超过一屏就提交（另外每 48 次绘制也提交），让每次等待都远低于 100 ms；任何一次等待达到 90 ms 记为一次超时复位，开机以来的次数显示在手表状态页和插件里，前几次写进日志。旧版自检把全部探针放进一次提交，第 5 个探针一旦让 GPU 卡住，超时复位就把后面的探针全部丢掉。
- **GPU 地址与缓存**：真机日志显示，GPU 往 PSRAM 带缓存别名（0x3C…）写的内容在 `vg_lite_finish` 之后仍停在 CPU 缓存里（非缓存地址读到旧内容，刷一遍缓存后才出现），而 GPU 读贴图时走带缓存别名比非缓存别名（0x38…）快一倍（启动测速：32 位贴图 6.6 / 11.6 ms 每屏，8565 5.3 / 13.6）。所以自检的目标（GPU 写、CPU 读回）用非缓存别名，帧里的贴图、背景图和批量命令流用带缓存别名，CPU 写完照常回写缓存；直接绘制的目标在片上 SRAM，不经缓存。
- **按 GPU 实测速度切分提交**：第六次真机日志显示，所有功能都关着也会一阵一阵地超时（每次都卡在等上一批或等整帧：118 ms / 235 ms），不超时的时段这套画法有 13–15 fps：动画的重阶段（层层叠加的半透明水面与光效）里，48 次绘制一批的 GPU 工作量超过了驱动的 100 ms。之前逐项试用把这些超时算到了正在试的功能头上（唯一判为可用的恰好是按面积提交）。现在模块启动时（加载角色之前）测一次 GPU：清屏、旋转缩放的 32 位与 8565 贴图（带缓存别名与非缓存别名各一次）、背景整屏贴图，各画满一屏三次取平均，得到每屏毫秒数，写进日志并显示在手表状态页；每次提交的像素量取最慢的贴图画法 25 ms 的量（八分之一屏到一屏之间），另外每 48 次绘制也提交。
- **GPU 功能逐项试用**：开机用最早在真机上稳定过的画法（32 位贴图、透明边缘、每次绘制单独调用驱动、背景按原样逐块画），画满 120 帧没有超时后一次只打开一项（原格式贴图、批量绘制、背景烘焙、边缘延伸），这一项再画满 120 帧、期间超时不到两次就算可用，超时两次就判为会超时并立刻关掉。结论保存在 `gpu-trust.bin`（版本 5；从版本 4 升上来时只重试批量绘制）；试之前先把正在试的项写进文件，手表若在试的时候死机重启，开机就把它记为会超时。只开着可用项仍在 10 秒内超时三次，就全部关掉重新试；全关还超时就歇 5 秒再画，从不暂停。每次超时后 1 秒内不开始新帧、也不在 LVGL 重绘里用 GPU；日志记下每次超时等在哪一步、等了多久，以及超时那一批里的每个绘制（标签、贴图页、混合、路径长度、包围盒、矩阵行列式）。手表状态页显示“GPU 功能：已开…；会超时…”。开发文件 `dev-gpu-timeout`（十六进制功能掩码）让带这些功能的帧假装超时，用来在 Mirage 上验证。
- **GPU 卡死的根因：长的三角形路径**：第八次真机日志记下了超时那一批的绘制：全是实时播放的图层里由 20–150 个三角形拼成的长路径（大量内部边），每次卡死的都不是同一个，而且成对出现（卡死一次，复位后的下一批又连带一次）；同一图层用预烘焙的轮廓多边形画时从不超时。现在实时绘制也画每组三角形的外轮廓（`bal2d-render` 的 `outline` 特性，手表版默认打开：共享边两两抵消，只留边界，覆盖的像素与三角形完全相同），此后真机再没有超时（只在试用批量绘制时）。中间试过把卡死那一批的绘制单独提交、找出“凶手”后跳过，结果凶手每次都不同，角色的零件一个个消失，已撤掉。退化的绘制（贴图到屏幕的仿射不是有限值、近乎奇异或放大超过 256 倍，或包围盒为空；真机上缩小到消失的附件会出现）不交给驱动；完全在裁剪区外的也不交。
- **批量绘制按驱动的写法**：Mirage 抓到的 9248 次驱动绘制里，驱动对每个寄存器都用单寄存器 STATE 写，并且在每条路径之前写 0x0A1B = 0x11000、0x0A3D = 0x3A9 和细分窗口；早先的批量命令流用多寄存器 STATE 写图像坐标生成器，也不写 0x0A3D，真机一开就卡死。现在命令流里每次绘制按驱动的顺序逐个写这 15 个寄存器再接路径（每次 128 字节加路径，在栈上拼好一次复制进去）。真机上还没验证过：手表会在逐项试用里自动重试它。
- **手表日志**：模块的 `log.txt`（每次开机最多 200 行，超过 96 KB 时上一份移到 `log-previous.txt`）可以在插件“手表上的性能”里点“导出手表日志”分块取回并保存成文件（协议 `LOG`）；`bal2d-link-cli log` 做同样的事。
- **按真机速度计时（Mirage 计时模式）**：普通模式下 Mirage 的时间随宿主机走，整数代码比 208 MHz 的 M33 快几倍，GPU 又是瞬间完成，测出的帧率既可能偏高也可能偏低。计时模式（qemu-miwear `dp-1700-exp` 分支 f2a682f1e5 起，Mirage main 2de2d12 起；说明见其 `emu/TIMING.md`）让每条指令按 130 MIPS 计时（208 MHz、每条约 1.6 个周期，含 PSRAM 缓存未命中），GPU 按 GC355 的建模时间完成，屏幕按 60 Hz TE 加 8 ms 传输。开启方式：在设备 `device.json` 的 `extraArguments` 里加
  `"-icount", "ips=130000000,align=on,sleep=on,exact-io=off", "-global", "driver=vsi.vglite,property=timing,value=on"`。
  这些参数来自芯片规格的估算，不是实测；有真机时，用手表上显示的各阶段耗时按 `emu/TIMING.md` 的方法校准。

  **按真机校准（2026-11-04）**：模块代码在真机上约相当于 `ips=50000000`（同一角色包、同样第 0 层实时第 1 层预烘焙、关批量绘制：动画 4.5 ms、绘制 56 ms，真机 4–5 / 56）；GPU 测速在 `mem-mbps=200` 时与真机一致（PSRAM 目标），而直接绘制的帧目标在片上 SRAM、只有贴图走 PSRAM，按 `mem-mbps=600` 才与真机的等 GPU 时间相当。固件代码（驱动、LVGL）在真机上跑得比模块快：校准后的模型里驱动约是真机的 2 倍、屏幕刷新约 23 ms（真机 6 ms），所以优化模块时看“动画 + 绘制”减去驱动与等 GPU 的部分。参数加在 `extraArguments`：
  `"-icount", "ips=50000000,align=on,sleep=on,exact-io=off", "-global", "driver=vsi.vglite,property=timing,value=on", "-global", "driver=vsi.vglite,property=mem-mbps,value=600"`。
  校准后（星野两层预烘焙、标记表盘、流畅优先）：逐次调用驱动时绘制 42.8 ms（驱动 23.8、等 GPU 6），按真机驱动开销换算约 40 ms 一帧（约 25 fps）；批量绘制时绘制 29 ms（驱动 0.8、等 GPU 10.5：GPU 成为瓶颈，星野每帧约 8 屏半透明填充）。白子 27 fps（模型里受屏幕刷新限制，真机应到 30 fps 上限）。
- **预烘焙提前加载**：星野 1.4 MB 的背景待机预烘焙在真机上一直没装上：最后加载时，压缩段的临时副本加 768 KB 余量放不下，背景图层每帧实时播放（真机上最大的 CPU 开销）。现在解析完骨骼后，只要总空闲减去预烘焙常驻部分和贴图、背景图、缓冲区将来要占的量还留得出保底（单块分配另查最大空闲块），就先装预烘焙，否则仍放到最后再试；上传每页贴图前先查堆（固件在 malloc 失败时直接复位），放不下就丢掉提前装的预烘焙，还放不下就让加载失败。解码预烘焙时原先保留了整块缓冲的容量（实际占用约是原始大小的 1.6–2 倍），现在收回（约 1.2 倍）。开发文件 `dev-skip-idle`（十六进制图层掩码）可让指定图层不装预烘焙。
- **实时绘制的 CPU**：摸头、对话时相关图层回到实时计算，每帧要分组并算轮廓。轮廓原先给 24 字节的边元组排序（经 memmove 搬动，占实时时一半以上的采样），后来改成打包的 u64 键排序，现在完全不排序：每个顶点挂一条出边链表，边 a→b 抵消 b 链表里一条还在的 b→a，否则挂到 a 上，再沿链表串成环（覆盖的像素不变，单元测试含折叠、翻转、重叠）。分组时先试三个顶点上次所在的组再全部扫描（调用数约少 17%）。校准模型里星野两层都实时时，绘制的模块部分约 145 → 70 ms（约 6 fps，换算真机约 8–10 fps）；剩下的主要是分组与蒙皮，要更快只能把对话动画也预烘焙。
- **预烘焙绘制的 CPU**：每帧的分组位置按调用变换、只平均用到的顶点（只有共享顶点才做除法），包围盒由形状的贴图坐标框四个角经仿射得到（再放宽 2 像素），逐帧解码不再每帧清空并交换每形状的数组（星野背景有 1977 个形状）。轮廓路径按每个环最多三个元素预留后直接写入，不再逐个检查。`idlecheck` 输出逐像素不变；校准模型里绘制的模块部分约 18 → 11 ms（逐次调用驱动时整帧换算真机约 36 ms，即 27–28 fps，GPU 每帧约 25–30 ms 与 CPU 并行）。`scripts/guestprof.py --func NAME` 反汇编一个函数里最热的指令。
- **预烘焙的大小上限**：预烘焙在手表上整个展开在堆里，和贴图挤在一起。原先只有角色包超过 2 MB 才把预烘焙帧率减半，Neru 的包 1.6 MB，预烘焙展开却有 2.6 MB，在手表上从来装不下，待机一直实时绘制（每帧约 700 次调用，是最重的大厅）。现在展开后的预烘焙合计超过 1.6 MB 也减半帧率（Neru 15 帧每秒、1.37 MB，装得下；矩阵在帧间插值，PSNR 与实时绘制相比 32 dB，和其他大厅相当）。
- **没有背景图时的预烘焙**：静态背景图（见上）在手表还没确认背景贴图不超时、自检里贴图不可用或内存不够时不用，这些槽位改按原样绘制；但预烘焙录制时这些槽位已经在背景图里，于是待机按预烘焙播放时那块地方是黑的（Neru 左上方的天空；真机上在“背景烘焙”试用通过之前也会这样）。现在背景图没用上时，每帧先把这几个槽位实时画出来（它们在绘制顺序最底部，从不移动）。
- **对话时不动的部分留在预烘焙上**：对话在待机循环上面播放（轨道 1、2 叠在轨道 0 上），很多大厅说话时场景大部分不动（Neru 的城市：728 个槽位里 667 个）。编译器把每段对话从待机循环的三个时刻起各播一遍，与只播待机的同一时刻逐帧比较，任何顶点偏离超过 0.25 像素、或附件 / 颜色变过的槽位算“会动”，其余写进主图层的预烘焙（动画里有绘制顺序时间轴的不做）。手表上对话进行中、镜头仍是待机镜头时，主图层照常摆姿势，但不动的槽位按预烘焙画，只有会动的槽位按绘制顺序分段实时蒙皮、分组，插在预烘焙调用之间。对话时角色会移开，所以这一层自己的“后画遮挡”区域此时不用。效果因大厅而异：Neru 对话帧的绘制 CPU 少约 28%（主机测量；画面与全部实时绘制相比 PSNR 34 dB，和待机预烘焙本身的误差相当），Hina 少约 7%，角色整个身体都在动的大厅（Shiroko、CH0335、CH0348）没有可留的部分。对话的姿势本身取决于开始时待机循环播到哪里（同一段对话从两个时刻开始，顶点平均差 3–6 像素），所以对话不能像待机那样整段预烘焙。
- **省掉看不见的填充**：GPU 每画一个像素都要读贴图、读写屏幕，不管这个像素最后看不看得见。参考大厅每帧有五分之一到一半的填充是白费的：贴图在那里完全透明，或者后画的不透明像素把它整个盖住（星野的水族箱背景大部分在她身后：每帧 8.5 屏填充里 5.6 屏看不见）。编译器逐帧播放预烘焙，分两部分省：
  - **透明的部分**与帧无关：三角形很大的附件（背景往往只有两个三角形）在预烘焙里换成均匀细分的网格（每条边在屏幕上约 48 像素一段），贴图在那里（连同周围 2.5 个纹素）全为零的小三角形不画。只在能省下至少 15% 贴图面积时才细分；轮廓直穿过、同一帧里又没有别的形状用到的细分点在加载时去掉（否则轮廓上挤满细分点，手表每帧要多变换许多顶点）。
  - **被盖住的部分**按屏幕算，背景在后面怎么动都不影响。编译器求出每帧都被后画的不透明像素盖住的像素（每帧区间首尾两个位置都要盖住，相邻调用之间的细缝先补上，再往里收 2 像素：抗锯齿的边从不算不透明），分两种：同一层里画在某个槽位之后的（每层选省得最多的一个切分点），和上面的图层（只在上面的图层也在播预烘焙时用：对话时角色实时在动，会移开）。剩下看得见的部分用至多 40 个矩形描述（可以重叠，GPU 按非零规则填充），写进角色包。
  - **手表上**：调用的包围盒碰不到任何可见矩形（查 16 像素格子的位图，几次比较）就整个不画，连驱动调用一起省掉；只有一个凸环、至多 8 个点的大形状（背景四边形）才按可见矩形裁剪，矩形整个落在四边形里就直接画这个矩形。更长的轮廓不裁剪：校准模型里把光束这样的长轮廓裁进二十几个矩形，CPU 多花的比 GPU 省下的还多。裁剪是省 GPU、费 CPU，哪边划算取决于手表在等哪一边，所以每个角色播预烘焙后，手表先把裁剪按秒交替关、开各 6 秒，比较每帧绘制加等 GPU 的时间，留下快的那种（日志 `idle clip: off … ms, on … ms`）。
  - 效果：每帧填充星野 8.51 → 5.96 屏，CH0335 8.09 → 6.78，Hina 7.95 → 6.86，其余参考大厅本来就几乎没有可省的。画面与不裁剪时逐帧比较：完全相同或只有个别像素中心正好落在边上的像素因路径取整翻转（PSNR 52–110 dB）。校准计时模型里星野两层预烘焙时，同样 150 秒画的帧数多 18%（13.6 → 14.9 fps）：等 GPU 从 6 ms 降到 1 ms，驱动时间也从 26 降到 13 ms（GPU 忙时驱动在等命令缓冲区）。编译多约 7 秒（插件的 wasm 里约 8 秒）。加载后有轮廓的形状不再保留三角形列表，星野的预烘焙在手表上反而比原来少约 70 KB。角色包里的预烘焙是格式版本 4，旧模块读不了会退回实时绘制，所以要同时更新模块；角色包重新导入后才有这项优化。

计时模式下参考大厅（编译为 `review/packs/v7`，Lua 表盘全屏，默认节奏，待机动画阶段，每个取 6 次采样平均）的帧率：

| 大厅 | fps | 动画 ms | 绘制 ms（驱动） | 等 GPU ms | 三角形 | GPU 调用 |
|---|---|---|---|---|---|---|
| Shiroko | 21.6 | 0 | 10.3（1.8） | 0.8 | 1721 | 88 |
| CH0184 | 13.0 | 3 | 25.8（8.0） | 1.2 | 3174 | 259 |
| Hina | 12.9 | 1 | 13.2（1.7） | 17.3 | 2190 | 109 |
| CH0335 | 12.3 | 1 | 25.3（4.0） | 4.7 | 1746 | 169 |
| CH0348 | 11.6 | 2 | 30.8（13.5） | 0 | 2944 | 367 |
| Hoshino | 10.8 | 3 | 35.0（6.2） | 0.8 | 4794 | 238 |
| Neru | 9.9 | 5 | 41.8（20.7） | 0 | 3199 | 632 |

（Yuuka 在另一次测量中为 14.9 fps。）上表是待机预烘焙之前、逐帧计算的结果。预烘焙之后（Lua 表盘，流畅优先，计时模式）：Shiroko 每帧自身约 7 ms、屏幕刷新约 17 ms，稳定在约 29 fps（30 fps 上限）；Hoshino 约 20 fps，此时瓶颈是 GPU 填充（每帧约 8 屏的半透明水面与光效，模型按 400 MB/s 显存带宽计）。直接绘制之后，Hoshino 约 24–25 fps（屏幕刷新从 17 ms 降到约 1 ms），批量绘制让驱动时间从约 7 ms 降到 0，模型里它仍受 GPU 填充限制（模型对片上 SRAM 与 PSRAM 用同一个带宽，低估了直接绘制在真机上的收益）。真机比模型慢约 3 倍，以手表上显示的分项耗时为准：第二次真机测试（预烘焙后）为 3.8 fps、绘制 90 ms（驱动 30 ms），据此加了直接绘制、批量绘制与更轻的节奏。同一构建多次测量会相差约两成，取决于采样落在动画的哪一段（Hoshino 的背景待机动画长 60 秒）。只按开场动画测的旧数字偏乐观：CH0335 的待机动画比开场重得多。

每帧还有约 18 ms 花在 LVGL 重绘与屏幕传输上。附件多、变形多的大厅（Neru 每帧约 460 个可见附件、CH0348 网格变形大）受驱动每次调用约 37 µs 的开销限制；这部分在固件驱动里，模块不能绕过它自己写 GPU 命令（那样在真机上风险最大）。

## 已知限制

- **双色染色（Tint Black）**：GPU 的图案填充只支持单色调制，使用暗色通道的槽位按普通染色绘制（插件预览图同样按手表的效果显示）。测试过的 8 个大厅都没有用到非黑色的暗色，因此没有可见差别。
- **语音**：对话动画会播放，但不播放语音。
- **性能数据**：上表来自 Mirage 计时模式的估算（CPU、GPU、内存带宽参数未经真机校准）；真机帧率以手表上“BA 大厅”应用或插件里的实时统计为准。模型里只有最轻的大厅接近 24 fps，重度的 10–13 fps；瓶颈在 CPU 一侧（蒙皮、把网格拆成仿射组、厂商驱动每次调用约 4700 条指令），GPU 光栅化本身只占很小一部分。
